# Verifying a result, and tracing lineage

DANCR records every step, so a project reruns the same way next month. This document describes the three
commands that turn that record into **evidence**: an *attestation*, a *verification*, and *lineage* / *proof*.

- `dancr verify <project> --record FILE` — write an **attestation**.
- `dancr verify <project> --manifest FILE` — re-run and check the project still reproduces it.
- `dancr lineage <project> NODE [--up|--down]` — what produced a step, and what depends on it.
- `dancr proof <project> NODE` — a one-node proof card.

The same three are MCP tools (`record_attestation`, `verify_pipeline`, `lineage`, `get_proof`) and Python API
names (`dancr.build_attestation`, `dancr.verify_pipeline`, `dancr.build_lineage`, `dancr.proof_card`,
`dancr.output_hash`, `dancr.attestation_hash`, `dancr.load_attestation`).

## The attestation

An attestation is one JSON file (`"kind": "dancr.attestation"`) that captures everything needed to check a
result without trusting the machine that made it:

- the engine version, the implementation version and the **code fingerprint**;
- the versions of the compute and read libraries;
- the project's dataset metadata;
- each source file's path, size and **content sample** (a cheap hash of its start/middle/end);
- for every step: its type, title, **plan hash**, row count, schema, and — for a step that stores a table — the
  **output content hash**;
- the numbers in every step's report, flattened to a `{path: value}` map, plus the finding sentence;
- every Answer's spec and its hash;
- an `attestation_hash` over all of the above (its `generated_at` and the hash itself excluded).

Recording is deterministic: the same project and data always produce the same `attestation_hash`.

## The verdict

`dancr verify` returns one of four verdicts and exits `0` only for `verified`:

| verdict | meaning |
|---|---|
| `verified` | engine, sources, every step's plan and output hash, the reports and the answers all match |
| `mismatch` | something differs (a source value, a result, a report number, an answer's spec) |
| `incomplete` | a source file or a step named by the attestation is missing |
| `engine-changed` | DANCR's own code or a compute library changed, so plan hashes are expected to differ; re-baseline |

`mode=stored` (the default) computes only steps not already in the cache; `mode=rerun` (`--rerun`) recomputes
every step — the strong claim. `--strict-sources` turns a changed source file into a mismatch rather than a
notice.

## How a result is hashed

`output_hash` is a stable content hash of a step's materialised table: the schema, the row count, and the sum of
per-row struct hashes. The sum is order-independent and the whole thing streams, so it costs one aggregate pass
over the result no matter how large. Any change to a value, a type or the row count moves the hash. Visual sinks
(charts, maps, reports, exports) are recorded but not bit-verified — a rendered PNG is not stable across fonts
and machines — so their **inputs** carry the proof instead.

## Lineage

Lineage answers two questions a graph alone does not:

- **up** — the chain of steps and source files behind a step (provenance);
- **down** — everything that depends on it: later steps, the **Answers** whose question drew on it, the **files**
  the project wrote, and the **Assistant turns** that built or discussed it (impact).

The Assistant part is read from the thread stored in the project (`meta["assistant"]`), so a source shows the
turns whose work consumed it.

## The proof card

`dancr proof <project> NODE` prints a compact, reviewable summary: the chain of steps with their plan hashes,
the source files with their content samples, the result's content hash, its row count and finding, the
assumptions an answer made on your behalf, and the exact `dancr verify …` command that re-checks it. Reports
generated by the **Report** step include a short provenance footer with a pointer to the same command (turn it
off with the report's *Add a provenance footer* setting).

## Standalone packages

An RO-Crate written by `dancr package --copy data` carries the pipeline, the data and the run manifest, so
`dancr verify` can check it on another machine without the original file paths.

## Guarantees

- **Nothing is inferred by a model.** Every number in an attestation comes from the engine.
- **The report says what it can prove.** Findings are compared with a tolerance; a mismatch names the exact
  report path that changed.
- **A failed check never hides.** The CLI exits non-zero; the MCP tool returns the full report whatever the
  verdict.
